# 产品目标与功能

> 最终确认版，2026-09-06 生效。本文及 ARCHITECTURE、UI、DECISIONS 是唯一现行规范；审计描述是历史证据，不是新开发约束。批准的当前实施范围仅为阶段 1 技术验证。

### 1. 产品定位与依据

已完整阅读用户提供的 D:/Downloads/ASTRA_MASTER_REFACTOR.md；其要求作为需求输入。用户最新确认与反馈优先于附件和旧方案。四份文档已正式化；后续阶段计划不构成连续编码授权。

现有产品是「标准菜单展示与维护工具 + 一次性定制导出器」。它已经积累有价值的菜品引用、名称覆盖、裁剪和离线文件能力，但没有客户、洽谈、持久化方案和正式报价版本，因此还不是销售工作台。产品定义为「面向酒店宴会销售的本地优先菜单洽谈与报价工作台」。核心资产是可以继续接待、追溯价格、重现交付物的一次客户方案。

销售和运营是两个工作角色，不必对应两套应用；客户不是账号或业务操作者。客户拿平板翻阅时属于销售控制的受限展示状态，不拥有修改、报价或导出权限。厨房通过应用外渠道收单及回复，不新增厨房账号、微信机器人、公开网址或二维码入口。

### 3. Feature Decision Matrix

KEEP 保留能力及可信规则；REFACTOR 保留业务、拆改实现；MERGE 合并为共同流程；REPLACE 用新实现替代；REMOVE 停止维护。为已确认的实施取舍，按阶段门禁逐项替换；不在技术验证期批量删除旧代码。

| 当前能力/遗留内容 | 决定 | 新归属与理由 |
| --- | --- | --- |
| 菜品库单一真源、套餐 ID 引用 | KEEP | 公共资产基础正确；历史版本通过冻结修订读取，不能随主数据漂移 |

| 运行期远程字体 | REPLACE | 本地字体包及可验收回退，离线同样可排版 |
| 旧二维码库、guest-mode CSS、不可达导出分支 | REMOVE | 已不服务业务；保留禁止公开入口的行为测试 |

| 测试与发布工具 | REFACTOR | 留下业务样例，剥离硬编码开发机路径、旧原型输出和结构断言 |

### 4. 业务问题与需求挑战

1. **报价不等于改一个总价。** 厨房回价对应一份明确菜单，后续换菜必须提示原厨房报价不适用于新内容；只议价则不必重复询厨。禁止单菜成本模型。
2. **询价单不是厨房执行单。** 厨房看到的是待核价方案，不能因“总厨定制单/备料参考”误开始备餐；执行排产、订单、合同与收款均不纳入 MVP。
3. **展示锁不是客户系统，也不是设备管理。** 客户能翻阅，但不能通过返回、搜索、深链或恢复进入其他范围；退出应用后能否阻止打开微信属于 Android 设备管理问题。
4. **“销售报价不能出现”与“客户正式报价菜单”需分清。** 受限标准菜单显示标准价；受限正式方案可显示销售明确选中的对客金额，不显示名为销售报价的内部编辑控件，更不显示厨房价、差额或议价历史。
5. **自动记录事实，不推测客户意愿。** 看过 2899 不等于倾向 2899，导出不等于发出、客户确认或成交。版本号也不能代替状态。
6. **不把降低换菜率变成限制客户。** 升级差异、出品结构由运营审核，最多突出几处差异；不设换菜次数上限、不弹强制理由、不让推荐盖过低价方案。
7. **引用单一真源与历史不变并不矛盾。** 公共主数据用于新方案，旧报价必须固定内容修订和媒体，不随菜名、图片、套餐价格更新。
8. **本轮不能恢复历史上从未保存的洽谈。** 本地草案没有落盘，仓库也没有客户记录；不能伪造客户、厨房回价和成交记录。
9. **价格仅指当前菜单每桌套餐价格。** 桌数仅是宴会资料，不参与厨房核价、报价有效性或价格计算；本系统不建立全场应收金额。

### 5. Information Architecture 2.0

```text
销售工作区（进入后记住身份；不每次重新填客户）
├─ 今日：快速接待 / 继续最近洽谈 / 待厨房报价 / 待跟进
├─ 标准菜单：宴席 → 套餐 → 菜品详情；最多两套餐差异比较
├─ 我的客户：搜索/最近接待 → 客户详情 → 洽谈时间线与方案
└─ 当前方案：菜单工作台 / 报价 / 版本；上下文内生成离线文件

受限展示状态（从菜单或已选正式方案进入，无一级业务导航）
└─ 授权宴席 → 授权套餐/单份正式方案 → 菜品详情 → 原展示位置

运营工作区（验证运营身份）
├─ 菜品库：分类 / 图片 / 信息 / 停用 / 使用情况
├─ 套餐编排：宴席 / 套餐 / 顺序 / 名称覆盖 / 推荐差异 / 效果预览
├─ 内容检查：临时菜治理 / 缺图 / 重复候选 / 无效引用 / 未使用
└─ 数据与系统：公共发布 / 销售身份 / 备份恢复 / 版本迁移 / 设置
```

不另设“我的方案”“我的报价”“我的版本”“导出管理”四套平行目录；它们均从客户或最近洽谈进入。导出是方案中的一级动作，而非强行增加一级导航。设置不承载高频报价动作。

### 6. 核心用户旅程与状态

固定评审人物：酒店宴会销售顾问，横屏平板，接待 10–60 分钟；只做情境推演，本轮未进行真实销售访谈。

| 步骤 | 销售动作 | 系统自动处理 | 返回/恢复 |
| --- | --- | --- | --- |
| 开始接待 | 点“快速接待”，选择宴席；可直接从菜单开始 | 建匿名洽谈、记录身份/开始时间 | 返回今日仍保留，无客户资料必填 |
| 展示 | 展示当前标准套餐；需要交平板时点“交给客户浏览” | 默认当前宴席和当前套餐，可一次扩展白名单 | 详情返回仅到授权套餐；重启仍受限 |
| 比较 | 点比较，选另一个套餐 | 价格差自动算，显示审核过的升级项，相同项折叠 | 回到原套餐和滚动位置 |
| 定制 | 取回恢复销售工作态，点“以此定制” | 固定标准套餐修订，创建草稿 | 再次打开继续原草稿，不重建 |
| 换菜 | 换菜→搜索→选中；无结果就用输入菜名 | 一笔命令保存，保留原基线、可撤销；临时菜仅属本方案 | 关闭选菜器不丢已有内容 |
| 询厨 | 生成厨房询价版 | 固定询价内容、编号、时间与版本；生成改动摘要 | 失败保留快照，重试不重复生成业务版本 |
| 回价 | 按微信回复录入整套餐每桌报价 | 自动关联当前内容的询价；编号无需输入；时间自动记录 | 改菜后旧价保留但标记需重询 |
| 对客报价 | 编辑当前对客报价，选小票或有图 | 冻结对客报价版；生成干净文件 | 导出不自动标记已发送/已确认 |
| 再谈 | 从历史报价“继续修改”或只改销售报价 | 新草稿指向父版本；旧版只读 | 可比较指定两版本，不覆盖旧价 |
| 确认留底 | 客户确定在酒店举办后点“客户确认方案” | 固定最终菜单、当前对客报价、客户与宴会资料、销售及确认时间 | 更正新增确认方案并关联原记录，不能覆盖原留底 |
| 后续 | 补称呼、电话、桌数、日期、备注或跟进日 | 汇总今日与客户时间线 | 数天后恢复最后工作位置 |

洽谈状态用进行中/待跟进/已结束；方案状态用草稿/待厨房报价/可对客报价/已报价/已确认/已归档。报价适用性另计算，不塞进一个几十种状态的枚举。无换菜标准菜单允许直接报价；厨房询价不要求先填厨房价或销售价。客户还没留下姓名时使用“今日 14:32 · 婚宴”作为可检索标签。

### 7. 主动补充的需求与 MVP 取舍

| 候选 | 谁/场景/频率 | 不做的后果 | 更简单方式与复杂度 | MVP |
| --- | --- | --- | --- | --- |
| 自动保存与最近恢复 | 销售，每次接待 | 切页或杀进程丢方案 | 本地事务保存，不做手动保存流程；中 | 必须 |
| 报价适用性校验 | 销售，每次再次换菜 | 旧回价错套新菜单 | 内容指纹匹配，避免审批系统；中 | 必须 |
| 询价编号与版本 | 销售/厨房，每次回价 | 微信回复匹配错方案 | 短编号+完整内部 ID，无微信接入；低 | 必须 |

| 内部备注与对客备注分开 | 销售，每次导出 | 泄露内部信息 | 默认内部，对客字段显式编辑；低 | 必须 |
| 菜品停用与引用检查 | 运营，日常维护 | 删除影响所有套餐 | 先停用后替换，删除受检查；中 | 必须 |
| 缺图、错误图片检查 | 运营，已有 14 道无图 | 现场空图和导出失真 | 列表筛选，不建设复杂评分；低 | 必须 |
| 临时菜治理 | 运营，重复出现时 | 自由输入污染公共库 | 人工加入/合并/忽略，候选只带菜名分类；中 | 基础版 |
| 跟进日期与今日待办 | 销售，经常 | 忘记回访 | 一个日期+应用内列表，不接日历；低 | 基础版 |
| 两套餐价值比较 | 销售，价格敏感场景 | 难以解释升级 | ID 差异+运营少量配对，不做 AI 销售话术；中 | 基础版 |
| 重复客户合并 | 销售，偶发 | 历史分散 | MVP 搜索并关联；自动合并会误并同家庭电话，复杂度中 | 自动合并后置 |
| 销售交接/多人实时编辑 | 离职或协作，低频 | 无法自动接管 | MVP 运营离线导入转交，留痕；实时系统高 | 实时后置 |
| 合同、订金、财务、厨房排产 | 其他团队，超范围 | 仍使用现有流程 | 不重复建设；高 | 排除 |

不新增客户画像、自动成交预测、销售排名、菜单 AI 改写、复杂折扣审批、多租户 SaaS 或消息推送。临时菜、历史记录与导出稳定性优先于装饰动画和主题数量。

### 8. 产品验收目标（待实机与销售试用验证）

- 无客户资料即可开始；库内换菜为“点换菜、输入搜索、点结果”，无保存/原因确认步骤。
- 临时菜在选菜器内完成，退出重进、离线重启后仍在；公共菜品库不自动增加。
- 关键离散动作提交成功才显示“已保存”；待保存/失败明确，失败不清空输入。
- 返回、横竖屏、杀进程、应用重开不能越过展示白名单；受限页不加载客户内部字段。
- 厨房能在短时间识别替换、新增、删除；目标 2 秒，必须由真实厨房人员试读确认。
- 客户文件无厨房价、内部备注和修改痕迹；原始标准菜单按原始标准价输出。
- 历史报价及客户确认版本可重开，公菜单更新后内容仍不变；同一导出记录可找到对应版本。
- 首次试点以两到三位销售完整走通接待→询厨→报价→再谈→客户确认闭环为准，不以页面数量验收。

### 9. 最终报价与确认规则

日常工作台只有一个主要金额“当前对客报价（元/桌）”。厨房参考价收在“录入厨房回价”和历史中，不设厨房报价、销售报价、成交价三个并列模块。厨房回价 2899 元后，销售决定对客使用 2999 元；系统保留两条来源明确的记录，客户只看到 2999 元。厨房回价不自动覆盖当前对客价。销售可明确采用参考价或输入其他价格。

只有换菜、新增、删除、菜品数量/份量或明确的做法核价条件变化才使旧价不适用于当前菜单。桌数、宴会日期、客户资料、跟进备注、纯展示排序、图片裁剪、英文说明等变化都不使报价失效。不能从自由跟进备注猜测核价条件；影响出品的调整应写入明确的核价字段。失效价保留在历史，界面提示“菜单已改，待重新询价”，不得作为当前有效正式报价输出。Undo 恢复同一核价内容后可重新适用匹配记录。

系统自动创建厨房询价完整 ID 和短编号，同一询价重试导出复用编号；新一轮询价生成新编号。销售无需管理、选择或填写编号。总厨仅回一个价格时，在当前方案直接录入；当前内容没有询价记录时系统一并创建记录。若当前菜单已不同于最近发给厨房的内容，保留输入，轻量提示核对“这次回价针对当前菜单还是上次发出的菜单”，显示菜单差异/时间而不要求编号。不得将明确属于旧版的回价自动应用新版。

客户最终确定在酒店举办宴席时形成不可变“客户确认方案”：最终菜单版本、最终对客报价、客户资料快照、宴会资料快照（含已知桌数/日期）、销售人员、确认时间。允许未知非必要资料为空，不阻断接待；后补或更正建立新确认修订，旧留底不漂移。它仅是合同价格与内部整理的参考，不表示已签约、收订金、收款或财务成交。系统不管理这些业务。
