# 已确定的重要决策

> 最终确认版，2026-09-06 生效。旧 D-001–009 与待确认 R 系列由本文完整替代；历史 Git 记录仅供证据，不具开发约束。用户已授权完成文档并进入阶段 1；阶段 2 及以后须另行确认。

## 已确认规则

1. 销售/运营两种角色，客户不是系统用户；允许销售控制的客户受限浏览。无客户账号、公开链接、二维码或自助改菜。
2. Android APK 本地优先；React/TypeScript/Vite + Capacitor + 原生事务持久化优先验证，全 Kotlin 为验证失败后的备选。不得直接 PWA 套壳；旧 PWA 保留为迁移前基线。
3. 当前菜单每桌套餐价格是唯一报价单位。桌数只是宴会资料，不参加核价、计算或有效性判断。日期、客户和跟进资料亦不影响报价。
4. 只对换菜、加删、数量份量与明确核价内容变化重新询厨。一个当前对客报价 + QuoteRecord 变化历史 + CustomerConfirmation 留底；不建三套并行业务模块。厨房参考价不能自动覆盖对客价。
5. 自动短询价号，销售无编号操作；总厨仅回价时当前方案直接录入。仅旧版语境冲突时核对菜单内容。
6. 客户确认方案冻结菜单、最终对客价、客户与宴会资料、销售和确认时间；不管理合同、订金、收款、财务确认。
7. 客户受限投影与返回边界由原生/数据接口共同约束；恢复方式验证低摩擦重复交接，不将每次 PIN 写死。普通 APK 不承诺禁止进入其他应用。
8. 今日、我的客户、时间线、续接、库选/临时菜、自动保存、Undo、低弹窗为正式方向；套餐价值由运营审核。
9. 厨房、客户无图小票、客户有图是三个独立模板，输出自包含 PNG/PDF，应用外人工传递；保留无图小票风格。
10. 菜库引用真源与历史冻结共存；迁移先备份副本，禁止按菜名盲合并或覆盖真实数据。WebDAV 只作内部公共单发布者与私人分区备份，后续阶段才实施。
11. 正式规范只维护四份 docs；README 为入口，AGENTS 为开发规则。验证源码/测试在 src/stage1，构建产物不提交，不恢复旧已删除原型。

## 最终确认版变更摘要

本次删除“旧规范 + 新提案”双轨规则；取消纯前端 PWA、固定左右布局和强制完整暗色约束。报价模型由三套价格实体收敛为统一报价历史与确认快照；明确桌数/日期/客户资料不影响报价。厨房短号全自动，客户取回优先会话内低摩擦，阶段 1 实测后才定恢复方式。全部后续实施与验收用“客户确认方案”替代原“成交留底”术语，明确排除财务业务。

## 阶段 1 历史验证记录（2026-09-06，仅作证据）

已完成的可复现部分：旧基线 `cd src && npm test` 全部通过；构建重新生成并校验 Service Worker 缓存键；`src/stage1` 的 React/TypeScript/Vite 独立原型通过构建；3 个领域测试通过（每桌金额校验、报价指纹排除桌数/日期/客户/跟进/展示排序/图片、换菜/加删/份量/做法变化与 Undo）。原型仅使用合成菜单数据，包含客户受限态、会话内滑动恢复和自动询价短号的接口占位，不连接生产数据。

尚未完成且不得宣称通过：原生事务数据库、杀进程后恢复、Android 返回/冷启动恢复、实际 PNG/PDF 保存与重新打开、离线中文字体、100 道菜分页在 Android 上的内存压力、低内存设备测试、三种导出模板的真实文件验收。原因是工作环境没有可用 JDK/Android SDK/adb；准备工具链的外部安装请求又被自动审批以用量限制拒绝。浏览器构建中字体资源缺失警告也证明不能把当前结果当作离线字体通过。

阶段 1 路线结论：Hybrid 方向尚未被证伪，也尚未被证明。现有证据支持继续保留 React/TypeScript/Vite + Capacitor + 原生窄接口的验证计划；全 Kotlin 不应仅因环境缺失而切换。下一步必须在可用 Android SDK、JDK 和测试平板/模拟器环境中补齐上述门禁，先提交实测结果，再决定进入阶段 2。阶段 2、真实数据迁移和完整 UI 均暂停。

## 阶段 1 云端构建与真机门禁（2026-09-07 生效）

用户已改为 GitHub Actions 云端构建，不再要求本机 Android SDK、adb 或模拟器。工作流入口 `.github/workflows/stage1-apk.yml` 是 GitHub 固定目录要求的唯一例外；全部实现、资源准备与构建脚本仍位于 `src/stage1`。PR 更新和 main 的 stage1 变更自动构建，也提供 workflow_dispatch（工作流进入默认分支后可在 Actions 手动选择分支）。不自动合并 PR、不上架商店、不部署生产。

APK 应用 ID 固定 `hotel.shanshui.validation`，显示“山水技术验证”，Android 最低 API 24，目标/编译 API 36。只构建 assembleDebug，使用云端临时测试签名，不需要生产密钥或仓库 Secret。每个新 runner 的测试证书可能不同，跨构建安装遇到签名不一致时只能先卸载旧测试包，卸载会清空合成测试数据；不要用这种方式测试正式数据升级。签名与 APK SHA-256 随产物记录，不上传私钥。若以后需要保留测试数据连续覆盖安装，再单独配置稳定的测试签名 Secret。

CI 只检出 stage1 与文档，不读取生产菜单配置；APK 不请求 INTERNET 权限，不接 WebDAV、不导入真实业务数据、禁用系统云备份，文件提供器仅开放本应用 exports 子目录。GitHub Actions 产物包含 APK、校验和、证书信息、应用清单、构建提交标识和本文测试清单，保留 14 天；私有仓库下载需要有权限的 GitHub 账号，链接不是公开客户菜单入口。

原生原型提供 SQLite 状态/事件同事务提交、故障注入回滚、持久化受限状态、会话内按住滑动恢复及冷启动设备凭证恢复。三种基础输出使用合成菜名，照片版使用程序生成的测试图，随包 Noto Sans SC 字体及 OFL 许可；按页生成 PNG 与原生 PDF，生成后校验 PNG 尺寸及 PDF 页数。它尚不是正式厨房差异单、完整报价历史或完整业务工作台。原生照片版用于验证图片解码与嵌入，不作为菜品摄影质量验收。
