# 山水S酒店 · 婚宴菜单系统（项目介绍 / 价值说明）

> 本文档面向「想快速理解这个项目、并帮忙提意见 / 评估价值」的协作者（包括其他 AI）。
> 配套设计稿见 `prototype/design-spec.svg`。

---

## 1. 这是什么

一个**面向婚宴 / 宴席场景的平板菜单系统**，运行在 iPad、手机等触屏设备上。
酒店员工用它在现场向新人/宾客展示宴席菜单，也可以在后台维护菜品与套餐。

一句话定位：**把一叠纸质婚宴菜单，变成一台可交互、可维护、可跨设备同步的平板 App。**

- 形态：单页静态 Web 应用（PWA），可"添加到主屏幕"当作原生 App 使用，断网也能看。
- 技术：纯 HTML / CSS / 原生 JS，无框架、无构建步骤、无后端依赖。
- 目标屏：iPad 横屏 1280×800 优先，手机竖屏自适应。

## 2. 给谁用、解决什么痛点

| 角色 | 痛点（纸质/旧方式） | 本系统带来的改变 |
|------|------|------|
| 酒店销售/宴会统筹 | 菜单改价、改菜要重印、易出错 | 后台改一次，所有设备即时同步 |
| 前台/服务员 | 向宾客介绍菜品靠口述、缺图 | 平板图文并茂，点开看大图+介绍 |
| 新人/宾客 | 纸质菜单静态、无重点 | 可滑动浏览、分类清晰、突出招牌菜 |
| 管理者 | 多宴席多套餐菜品重复维护 | 菜品库统一管理，图片只存一份 |

## 3. 核心功能

**展示端（点菜模式）**
- 宴席切换（婚宴 / 宝宝宴 / 订婚宴 / 尾牙 / 乔迁，可扩展）
- 套餐档位切换（如 A/B/C/D 四档宴席）
- 菜品卡片网格（4:3 缩略图 + 中英文名 + 分类标签），点开看大图与介绍
- 搜索菜品
- 大图跨分类循环浏览（上一张/下一张）

**管理端（后台）**
- **菜品库**：所有菜品主数据集中录入，图片只存一份；一处修改，所有含该菜品的菜单同步更新
- **菜单组装**：从菜品库勾选菜品加入套餐，支持批量应用到多个套餐
- **拖拽排序**：套餐顺序、套餐内菜品顺序均可拖动调整
- **图片展示位置裁剪**：4:3 取景框，支持上下左右平移 + 缩放（WYSIWYG，所见即所得），管理端/点菜端/选择器统一渲染
- **批量新建菜品**：一次导入多张图片，自动建"待命名"菜品，再逐个改名
- **内联改名**：点菜名直接改，含重名校验
- **数据迁移**：导出/导入 JSON 配置，跨设备搬运菜单

**系统**
- PWA：可安装、离线可用
- 数据持久化在本地（localStorage），按设备隔离

## 4. 技术架构（关键点）

```
index.html
  ├─ assets/data.js      # 种子数据（菜品库 LIBRARY_SEED + 菜单 MENU_DATA）
  ├─ assets/store.js     # 数据访问层 Store（localStorage 持久化，已标注"后端接入点"）
  ├─ assets/app.js       # 全部 UI 逻辑与渲染
  ├─ assets/style.css    # 样式（设计令牌见 design-spec.svg）
  ├─ sw.js / manifest    # PWA 离线
```

**数据模型（两层解耦，这是设计的核心）**
- **菜品库 library**：菜品的唯一主数据（名称/英文名/分类/介绍/图片 base64/裁剪位置）。
- **菜单 menu**：每个套餐的 `dishes` 只保存**菜品库 id 引用**（字符串数组）。
- 好处：同一道菜出现在多个宴席/套餐时，图片只存一份；改一处，处处同步。

**图片裁剪模型**
- `crop = { x, y, w, h }`（图片归一化裁剪矩形）
- `h = w × 0.75 × 图片宽高比`，保证取景框恒为真实 4:3、图片不变形
- 展示端用 `background-size / background-position` 精确还原，编辑框所见 = 点菜页所显

## 5. 价值主张（为什么值得做）

1. **轻量零运维**：无需服务器、无需数据库、无需应用商店上架，丢台 iPad 打开链接就能用。
2. **维护成本极低**：非技术人员也能改菜单、换图、调顺序。
3. **婚宴场景专属**：分类（凉菜/主菜/主食点心）、四档宴席、4:3 美食缩略图，贴合酒店真实业务流程。
4. **可演进**：Store 层已预留"后端接入点"，将来接服务端只需替换 localStorage 调用，不影响上层逻辑。
5. **可沉淀**：菜单数据可导出为 JSON，是酒店的数字资产，能持续复用与迭代。

## 6. 现状与待补（坦诚说明）

- 当前 A/C/D 三档套餐为示例数据（`demo: true`），**正式菜品待补充**。
- 除婚宴外，其他宴席类型（宝宝宴/订婚宴/尾牙/乔迁）**暂无数据**，结构已预留。
- 菜品**真实照片尚未录入**，现多为占位。
- 菜品介绍 `desc` 为示例文案，待替换为正式介绍。
- 数据目前**按设备本地存储**，跨设备实时同步需接入后端（架构已留好接入点）。
  - 当前跨设备方案：导出 JSON → 另一台设备导入；或把 JSON 提交到仓库/部署目录后"从云端拉取"（已实现/规划中）。

## 7. 想请其他 AI 帮忙评估的问题

1. **价值层面**：在"酒店数字化转型"语境下，这个轻量方案 vs 重 CRM/餐饮 SaaS，性价比与适用边界在哪？
2. **产品层面**：婚宴场景还有哪些高频动作值得产品化（如：扫码看菜单、宾客点选忌口、打印喜庆请柬式菜单）？
3. **设计层面**：见 `design-spec.svg`，视觉层级、配色、间距、响应式列数、裁剪器发现性、无障碍（WCAG AA）是否需要优化？给出可直接落地的 CSS 建议。
4. **技术层面**：要支持"多门店/多设备实时同步"，最小可行的后端形态是什么（静态 JSON + 定时拉取？还是 WebSocket/CRDT）？
5. **增长层面**：这类工具如何自然地从"内部展示"延伸到"宾客自助/营销"（如分享菜单到朋友圈）？
