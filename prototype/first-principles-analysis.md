---

## 一、系统本质（第一性原理）

剥掉所有 UI 细节，这个系统到底是什么？

**它是一台「菜品主数据 → 宴席/套餐 → 客人视图」的映射编辑器 + 展示器。**

- **输入**：菜品主数据（图、中/英文名、分类、价、介绍、裁剪框）。
- **组织**：按「宴席（婚宴/宝宝宴/…）→ 套餐（A/B/C 档）→ 菜品」三层组装。
- **输出**：客人平板上能看懂、能决策的菜单（菜长啥样、多少钱、叫什么）。
- **维护者**：运营者（你），核心诉求是「低成本把这套映射维护对、改得快」。

**最小必要功能 = 主数据 CRUD + 套餐组装 + 客人展示 + 低成本维护。**

任何不在上述闭环里的功能，都要反问：它服务了谁、解决了什么真问题？

## 三、从第一性原理看「需要补齐」

### P0 — 最值得做（影响"系统可信"与"维护成本"）
1. **单一可信源 / 防丢**
   - 现状：数据存在各设备 localStorage，清缓存/换设备即失；当前靠"导出 JSON"或"云端拉取"手动搬运，依赖人记得做。
   - 第一性原理：菜单是酒店运营资产，应有**单一可信源**，且**不易丢**。
   - 建议：变更即自动备份到 `menu-config.json` 并触发重新部署（或本地定时快照 + 一键恢复）。
2. **菜品介绍在点菜端"卡片层"是否要露**
   - 现状：介绍仅在详情弹窗可见，列表卡片只显名+价+图。
   - 建议：确认运营是否需要卡片级一句话简介（多数婚宴场景不需要，详情够用）→ 大概率**不做**，记一笔即可。

### P1 — 明显缺口
3. **分类/宴席内容补全**（内容缺口非功能缺口）
   - A/C/D 档真实菜品、宝宝宴/订婚宴/尾牙/乔迁等宴席类型、真实菜品照片、正式介绍文案待补。
   - 这是"填内容"，不是"加功能"，但阻塞系统真正可用。
4. **撤销 / 历史**
   - 现状：改名、排序、删菜均无撤销，误删菜品库即丢。
   - 第一性原理：低成本维护的前提是"错了能回"。
   - 建议：至少加"删除菜品库确认 + 最近一次操作可撤销"，或本地操作日志。

### P2 — 体验优化
5. **价格编辑便捷性**
   - 客人最关心价格，运营改价频率不低，但套餐价藏在"编辑套餐"弹窗。
   - 建议：列表/卡片内联编辑价（点价格即改），降低改价摩擦。
6. **多设备实时同步**
   - 已知取舍（你已明确暂不需要后端）。记录为"有意为之"，非缺陷。

## 四、从第一性原理看「不必要 / 可精简」

### 冗余入口（同一目标多条路径）
1. **两条改名入口**
   - 现状：列表内联改名（点菜名直接编辑）+ 弹窗改名（点卡片开弹窗，含中/英+恢复）。
   - 问题：两处都能改中文名，逻辑分散、行为易不一致。
   - 建议：**统一为弹窗**（内联改名移除），弹窗一次管好中英文名 + 恢复，更清晰、可维护面更小。
2. **搬菜入口重叠**
   - 现状：设置里「从云端拉取菜单」（拉仓库 JSON）+「导入配置 JSON」（选本地文件）+「导出配置」（下载）。
   - 问题：「云端拉取」与「导入」最终都往本机写菜单，目标重叠。
   - 建议：保留「导入配置」作离线兜底，**云端拉取作为主路径**，或在 UI 上合并为"从来源载入菜单"（二选一即可），减少认知负担。
3. **两套菜品排序**
   - 现状：卡片手柄拖拽 + 文字排序（本次新增，因卡片不灵敏）。
   - 问题：菜品排序两套交互，维护面翻倍。
   - 建议：卡片拖拽既然不灵敏，**只保留文字排序模式**，移除卡片手柄拖拽，减少代码与测试面。

### 可能过度的视觉/交互
4. **两条看详情路径**
   - 现状：点菜大图跨分类循环 + 详情弹窗。
   - 建议：确认两者体验是否真重叠；若重叠，合并为详情弹窗（大图+介绍+价），砍掉独立循环浏览。
5. **设置项密度**
   - 现状：批量新建 / 云端拉取 / 导入 / 导出 / 恢复默认 并列。
   - 建议：已部分折叠，可再分"运营常用"与"高级"两层，降低新手上手成本。
